# AI 屎山信号清单（ai-slop-signals）

本文件是评估维度 4「AI 屎山与许愿痕迹」的取证清单。每条信号给出识别方法、正反例、扣分指导。

**判断原则**：不是"出现过 AI 味就扣分"，而是**"这些痕迹是否已经影响人类维护"**。零星残留（一两个未使用导入）属正常开发残留；成规模、集中污染、影响阅读和修改的才是屎山。

**核心区分（最重要的概念）**：
- **人类正常债务** = 复制粘贴、死代码、个别大文件、个别死导出。人类维护的项目普遍存在，只要不显著妨碍理解与修改，**不重罚**。
- **AI 过程指纹** = 为 AI 编码过程写的注释/标记、AI 排查残留混入热路径、面向 AI 工作流的结构、系统性 god-file/god-function。这是 vibe coding 的本质特征，**重罚**，可触发 `scoring-rubric.md` 的结构性硬闸门。

---

## 许愿检测协议（MUST，评估任何项目都先做）

1. **列承诺**：读 README / 文档 / 模块说明 / 关键 docstring，列出声称的能力、性能、架构、扩展性承诺（摘录原文，记 `文件:行号`）。
2. **逐条验证**：去代码里找实现证据，重点反向查：
   - 声称「性能优化 / 高性能」→ 是否真降低复杂度/开销，还是新增开销（多余抽象层、全量复制、冷路径缓存、嵌套循环无谓工作）。**声称优化却更慢 = 最典型的许愿信号。**
   - 声称「可扩展 / 模块化」→ 抽象是否有真实第二实现、真实扩展点，还是唯一实现纯装饰。
   - 声称「支持功能 X」→ 真实现，还是占位/TODO/半成品/抛错兜底。
3. **记证据**：每条核对结论带 `文件:行号`。验证不通过的记入「AI 屎山专项发现」。

**典型许愿特征**：README 承诺一堆特性但代码里没有；改动没有理由可自证（"用了 XX 模式所以好"）；优化没有测量支撑；宣称的架构与实际代码形态对不上。

## 信号 1：承诺-实现背离（许愿，最严重）

**识别**：声称的能力/性能/架构在代码里验证不成立，甚至反向成立。这是 vibe coding 的本质——操作者只会许愿，AI 制造"看起来在干活"的代码。

**反例**：
```python
# README：本项目通过多级缓存 + 异步批处理实现 10 倍性能提升
class CachedProcessor:
    def __init__(self):
        self.handlers = []          # 装饰性抽象，只有这一个实现
        self._setup_pipeline()      # 每次调用重建整条管道

    def process(self, items):
        for item in items:          # 声称"批处理"，实际逐条同步处理
            self.handlers[0].handle(item)
        return sum(i.cost for i in items)  # 每次全量重扫，O(n) 重复计算
```

**正例**：
```python
def process(items):
    # 实测：数据量 <1 万时直接循环最快，等有真实瓶颈再优化
    return [handle(item) for item in items]
```

**扣分**：一处重大许愿证据（如声称的性能优化实际加开销）即重大信号，维度 4 ≤70；≥3 处压到 ≤45。

## 信号 2：源码内联的 AI 过程标记

**识别**：注释看起来"齐全"，但完全是写给 AI/清单/检查器看的，不是给人看的。只统计**源码文件内**（如 .py/.ts/.cpp）的 AI 审查/排查留痕：
- 每个函数都有完整 docstring 但复述签名/操作（"该函数用于处理数据并返回处理结果"），没增加信息。
- 注释密度异常高且都是短注释复述代码。
- 真正难的地方反而没有任何解释。
- **面向 AI 编码过程的标记/留痕**（最直接证据）：如 "Codex P1/P2" 审查标记、`@anchor.probe(...)` 探针协议引用、agent 排查过程说明——这类注释只有 AI 编码代理需要，人类维护者必须逐一过滤才能读。

**排除项（不算过程标记）**：AGENTS.md / CLAUDE.md / .github/instructions / copilot-instructions 等**顶层约定与文档文件**，是正常工程实践；AI 辅助工具链（CI、agent 配置）也不构成。**只有源码文件内联的 AI 审查/排查留痕才算。**

**判定标准**：一条注释，人类维护者需要它吗？还是只有 AI 编码代理需要它？

**反例**：
```python
# (Codex P2) 修复 #2841：此函数修改后需同步更新 main_routers 的 monkeypatch 绑定
def process_data(data): ...
```
人类维护者看到的是 AI 审查轮次的元数据。

**正例**：
```python
# 只取 value：调用方不需要 key，过滤掉省内存；空表直接返回，调用方展示空态
def process_data(data): ...
```

**扣分**：成规模（≥3 处清单式）→ 维度 4 ≤70；源码内联的 AI 过程标记 ≥5 处、散布于核心/热路径文件且显著妨碍阅读 → 触发硬闸门 G3（总分 ≤50）；整文件逐行复述 → ≤45。

## 信号 3：AI 排查过程残留混入热路径

**识别**：AI 排查 bug 的循环过程没清理干净，直接留在核心代码里：
- 热路径采样函数内嵌坐标特定的调试块（`if (debug && pos.x==728 && pos.y==-8) fprintf(...)`）。
- 17 个 `WG_*` 之类 env 开关、每次执行都检查的魔法偏移内存校验（`IsBadReadPtr(base+0x34001)`）。
- 源码文件头部嵌着几百行排查过程日志（"第 1 轮修复复盘"）。
- 大量探针程序与主程序复制同一份参数表。

**识别**：挑最热的采样函数看有没有调试插桩；Grep `getenv|fprintf|IsBadReadPtr|debug|TODO 排查` 等；统计 env 开关数量；看 `.artifacts/`、`.investigations/` 这类过程目录是否存在（它们是"AI 操作者让 AI 反复乱搞"的物证，本身是 AI 过程指纹）。

**扣分**：热路径调试残留合计 ≥5 处 → 触发硬闸门 G4（总分 ≤60）；成规模 → 维度 4 ≤45。

## 信号 4：结构性 god-function / god-file（大且混杂）

**识别**：核心业务逻辑集中在极少数超大函数/超大文件，**且职责混杂、难以追踪**——大但职责单一、逻辑清晰、注释完善的不算（企业长流程不硬拆）：
- 核心业务逻辑集中在单个 >500 行函数（god-function）且混杂多类不相关职责。
- 单个 >2000 行文件（god-file）且混杂多个不相关子域（如大量状态类型混在一个视图文件）。
- 巨型前端组件（数千行单文件）、门面 re-export 数百个名字、monkeypatch 耦合测试结构。

**识别**：统计最大函数行数、最大文件行数 + 职责审查；追一个用户高频路径看是否要跨 god-function 才能理解。

**扣分**：核心 god-function/god-file（**大且混杂**）→ 触发硬闸门 G1（总分 ≤60）；这类项目的维度 2（可追踪性）也应相应压到 ≤45。

---

## 信号 5：god-file 逻辑混杂

**识别**：核心业务逻辑挤在极少数超大文件/超长函数里，「一个文件什么都有」——配置、状态、UI、业务、IO 混在一起；或逻辑被抽象层切得支离破碎只有 AI 能拼起来。

**反例**：`main.py` 3000 行，从配置解析到 UI 渲染全在里面；核心函数 400 行，中途改全局变量、夹杂 IO。

**正例**：业务按职责分布在对应模块，文件边界与逻辑边界一致，单函数 <100 行。

**扣分**：核心逻辑集中在 1-2 个 god-file 且职责混杂 → 维度 2 与维度 4 同时重罚；超过闸门阈值（>500 行核心函数 / >2000 行职责混杂文件）→ 触发 G1。

## 信号 6：幻觉注释

**识别**：注释提到的函数/文件/参数/行为在代码里不存在或与事实矛盾。

**反例**：
```python
# 调用 get_cached_data 加速（配置见 redis_client）
data = fetch_from_db()  # get_cached_data 早已被删，redis_client 从未存在
```

**正例**：
```python
# 直接查库不缓存：该接口调用频率极低（日均个位数），不值得引入缓存层
data = fetch_from_db()
```

**扣分**：1 处即重大信号（维度 4 ≤70）；≥3 处压到 ≤45。

## 信号 7：复述型注释（只描述操作，不讲述原因）

**识别**：注释把代码翻译成自然语言，无新增信息。

**反例**：
```python
# 循环遍历列表中的每一项
for item in items:
    # 如果 x 大于 10 则执行加法
    if x > 10:
        total += item.value  # 把结果加到总和中
```

**正例**：
```python
for item in items:
    if x > 10:
        # 阈值取 10：低于此值是噪声数据，不参与求和
        total += item.value
```

**识别技巧**：逐行注释频率高、每行都能从代码秒懂，即为复述型。注释密度 >30% 且多为短注释时重点抽查。

## 信号 8：死代码与未使用导入

**识别**：未使用导入（`grep` 每个导入名）；定义了但从未被调用的函数/类；注释掉的整块代码留在交付源码。

**反例**：
```python
import os, sys, json, random, hashlib  # sys/random/hashlib 全文从未使用

def legacy_parse(data):
    """旧版解析逻辑，已废弃"""
    # ... 数百行从未被调用的代码
```

**正例**：无未使用导入；废弃逻辑删除，用 git 历史保留。

**扣分**：整段死函数成规模（≥3 处）或注释掉的整块代码在交付源码 → 维度 4 ≤70。

---

## 信号 9：过度工程（为简单问题套模式）

**识别**：10 行能解决的问题，套上工厂/抽象基类/观察者/多层接口，没有调用方、没有扩展预期，只为"显得正规"。

**反例**：为一句 `print` 引入 `Protocol` + `ConsoleSender` + `SenderFactory`，全项目只有一个调用方且不会有第二个实现。

**正例**：
```python
def send_message(msg): print(msg)  # 当前只有控制台一种实现，等有第二种再抽象
```

**扣分**：一处装饰性抽象即信号；同一项目 ≥3 处模式套壳 → 维度 4 ≤70。

## 信号 10：无效抽象与不必要的间接层

**识别**：函数/类只是"转一手"，原样转发，中间无任何逻辑、校验或转换。

**反例**：
```python
def get_user_name(user_id):
    return _fetch_user(user_id).name

def _fetch_user(user_id):
    return database.query_user(user_id)
```

**正例**：有实际职责（缓存/校验/转换）的包装才是正当间接层。

**识别技巧**：函数体只是"调用另一函数并原样返回"且无边界处理，即为无效转发。深链转发（A→B→C→D 每层无逻辑）是高发区。

---

## 信号 11：无意义防御（吞异常、永假条件）

**识别**：`except`/`catch` 空块、`pass`、`print`，错误被无声吞掉；不可能为空的变量做空值检查；`if x != None and x is not None` 式重复判断；到处 try/catch 把 bug 藏起来。

**反例**：
```python
try:
    result = risky_call()
except Exception:
    pass  # 出错就静默，调用方永远不知道失败

if data is not None and data != None:  # 重复检查，且 data 一定非空
    ...
```

**正例**：
```python
try:
    result = risky_call()
except TimeoutError:
    # 超时是可预期的：重试，重试仍失败则向上抛，让调用方决定
    result = retry(risky_call, times=3)
```

**扣分**：成规模（≥3 处吞真实错误）或"空块 catch 包裹关键业务逻辑" → 维度 4 ≤70。

---

## 信号 12：复制粘贴变体（DRY 破产）

**识别**：多段逻辑几乎相同、仅少量参数/命名不同，出现在不同文件或同一文件多处。每份变体都在被调用，不报错，但改 bug 要改 N 处。

**反例**：`calc_price_a` 与 `compute_price_b` 逻辑相同仅命名不同。

**正例**：
```python
def calc_price(items, tax_rate):
    """按税率计算总价，供订单与购物车两处复用"""
    return sum(item.price for item in items) * (1 + tax_rate)
```

**识别技巧**：对比函数体结构一致的代码块；同目录内函数名高度相似（`getX`/`getX2`/`fetchX`）时重点抽查。

**扣分**：这是人类项目也常有的**人类正常债务**——若只是少量跨模块复制粘贴、不影响维护，轻扣或不扣；系统性（≥3 组、每次改动要同步 N 处）才重扣。

---

## 信号 13：命名与功能不符

**识别**：函数/变量/文件名暗示的行为与实际实现不一致，直接误导读者。

**反例**：
```python
def get_total(items):
    """实际返回平均值"""
    return sum(items) / len(items)
```

**识别**：抽查函数名后核对函数体；文件名与目录结构对照实际内容。

---

## 信号 14：拼凑感与风格突变

**识别**：同一文件内多种命名/缩进/注释风格并存（`fetch_data`/`FetchData`/`fetchData` 混用），或同一问题在不同文件用了完全不同解法。AI 多次生成拼接的痕迹。

**识别技巧**：Grep 同类符号的命名风格统计；同文件风格互斥（≥2 种命名规范）即可判定。

---

## 信号 15：README 承诺未实现

**识别**：README 声称的功能/性能/架构，在代码里没有实现或实现不一致——这是信号 1（承诺-实现背离）在文档侧的体现。

**反例**：README 说"支持用户注册登录"，代码里根本没有认证。

**不算信号**：README 的广告、营销、赞助、捐赠信息；README 缺失或仅简略许可信息；README 不够整洁——都不构成信号。

**扣分**：README 承诺未实现时，随信号 1 记入维度 4；不单独扣"文档质量"分。

## 综合判定指导

| 信号密度 | 维度 4 参考分 | 对总分的影响（权重 30） |
|---------|--------------|---------------|
| 几乎无信号（≤1 处零星） | 85-95 | 加分，总分有上冲空间 |
| 个别信号（2-4 处，不集中，且为人类正常债务） | 75-85 | 中性，总分 ±5 |
| 成规模（≥5 处，或一处重大许愿，或一处 AI 过程指纹） | 45-60 | 显著下压，可能触发硬闸门 |
| 泛滥（每抽样文件命中 ≥2 类信号，或 AI 过程指纹遍布） | ≤40 | 触发硬闸门，总分落到 50 以下 |

**注意**：维度 4 权重 30。一处重大许愿或 AI 过程指纹足以压掉一个档位；触发了结构性硬闸门（G1/G3/G4）则总分直接封顶。**表面规范但设计荒谬——不要被注释/文档/命名/测试量骗了，回到信号 1（许愿）、信号 2/3（源码内联 AI 过程标记）、信号 4（结构 god）重罚。**

**取证模板**：报告里每条屎山发现按此格式写——
`文件:行号 —— 信号 X（<信号名>）：<具体描述>`
