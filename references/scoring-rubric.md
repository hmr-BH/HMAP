# 分维度打分标准（scoring-rubric）

本文件定义四个评估维度的 0-100 原始分打分细则 + 结构性硬闸门。打分时逐条对照锚点特征，取最贴近的一档，再按"部分符合"小幅上下调整（±5 以内）。**每个判断必须有 `文件:行号` 证据支撑**。

## 总则（打分前必读）

1. **这是人类可读 & 可维护性评估，不是代码规范审查。** 命名一致、注释齐全、DRY、文档完整、测试规范——**这些"规范"本身一律不得加分**。只有当它们真正让人类更容易理解与维护时才加分。AI 能伪造一切表面规范，伪造不了"人类愿意维护"这件事。
2. **核心判据（强制执行）**：打分全程锚定「这个项目交给你，你愿意亲自维护它吗？为什么？」，最终总分必须与该答案一致。若答案为"不愿意/不可能"而总分偏高，说明被工程表面（测试、CI、文档纪律）迷惑，必须按「结构性硬闸门」封顶并下调。
3. **区分「人类正常债务」与「AI 过程指纹」**（本细则最重要的概念）：
   - **人类正常债务**：复制粘贴、死代码、个别大文件、个别死导出——人类维护的项目普遍存在，只要不显著妨碍理解与修改，**不重罚**，不因此降出 90 档。
   - **AI 过程指纹**：为 AI 编码过程写的注释/标记、AI 排查残留混入热路径、面向 AI 工作流的结构、系统性 god-file/god-function——这是 vibe coding 的本质特征，**重罚**，触发硬闸门。
4. **结构性硬闸门**：存在使人类不可能/极难维护的结构性事实时，**总分硬性封顶**，维度加权分算得再高也必须封顶（见下一节）。
5. 权重：设计合理性与技术诚实性 25 / 可追踪性与心智负担 25 / 人类可读性与自我解释性 20 / AI 屎山与许愿痕迹 30。维度 4 反向计分。
6. 锚点分数用 90（优秀）、70（正常）、45（较差）、20（极差）四档描述；介于之间用 ±5 档取整。
7. 某维度证据不足时，取 70 基线并声明，不得因此虚高总分。
8. **顶端校准**：真正由人类精心维护、注释讲"为什么"、文档诚实、结构边界清晰的优质项目，应落在 **90 档（90-95）**。少量可接受的债务——测试偏薄但存在、个别/若干较大文件但职责可辨认、个别复制粘贴、个别风格违约——**不构成降到 80 档的理由**，除非它们实际妨碍了人类理解与修改。这是为了与"区分度"目标保持一致：顶端留给真实的人类项目，底部被结构性硬闸门封死。

## 结构性硬闸门（总分硬性封顶）

**意义**：这是"人类是否愿意/能够维护"的客观化判定。以下任一事实成立，说明该项目存在使人类无法或极难维护的结构性问题——此时无论四个维度的加权分是多少，总分都不得超过对应封顶。**多命中取最低封顶。** 每条命中都要带 `文件:行号` 证据。

| 闸门 | 判定条件（必须带证据） | 总分封顶 |
|------|----------------------|---------|
| G1 核心 god-function / god-file | 核心业务逻辑集中在单个 >500 行函数，或单个 >2000 行文件且职责混杂 | 60 |
| G2 体量超人类可维护 | 核心源码 >50 万行，且结构 god 化（命中 G1，或超大文件/超长函数普遍存在） | 40 |
| G3 为 AI 过程的注释/标记成规模 | 面向 AI 编码过程的注释/标记（如 "Codex P1/P2" 审查留痕、`@anchor.probe` 探针引用、agent 排查过程说明）≥5 处且分散在多个文件 | 50 |
| G4 AI 排查残留混入热路径 | 热路径代码内嵌调试块、env 开关、魔法偏移内存检查、源码内嵌排查日志，合计 ≥5 处 | 60 |

**叠加规则**：G2（体量超人类可维护）与 G3（为 AI 过程注释成规模）**同时**命中 → 封顶 **35**——同时存在"规模超出人类可维护 + 注释面向 AI 编码过程"的项目，是"只能靠 AI agent 维护"的原型（如 60 万行核心 + 上千条 Codex/CodeRabbit 审查留痕）。

**判据对照**：闸门封顶后，用核心判据复核——「你愿意亲自维护它吗？」答案"不愿意"时总分还应更低（≤60），"完全不可能"时 ≤40。若客观判断与封顶矛盾，以更严的为准。

**示例（仅示意，非真实证据）**：核心路由单函数 956 行（G1）；核心源码 127 万行且 god-file 普遍（G2）；源码内 500 处 "Codex P1/P2" 注释（G3）；采样函数内嵌 18 处 `if (debug && pos==...) fprintf`（G4）。

## 维度 1：设计合理性与技术诚实性（权重 25）

评估"这个项目的设计是否真的合理、承诺是否真的成立"——vibe coding 最常坍塌的地方。AI 操作者只会"许愿"：声称性能提升、声称架构优雅，但没有任何技术思维支撑。

| 锚点 | 特征 |
|------|------|
| 90 | 架构与问题复杂度精确匹配，小问题不套大框架；核心承诺全部经得起代码验证；关键决策有技术理由（有测量、有取舍说明）；存在真实测试（即使覆盖面偏薄）与可构建性，给维护者基本安全感。**允许少量人类正常债务**（个别模块间复制粘贴、个别大文件、测试覆盖不全）——只要不构成"设计是否成立"的问题，不降出 90 |
| 70 | 设计大体成立；个别抽象装饰性或个别承诺略有夸张；核心仍可维护、主要承诺能兑现 |
| 45 | 架构与问题不匹配；多个承诺无法兑现——尤其"性能优化"实际更慢、"可扩展"却无扩展点；决策像许愿，看不出任何技术理由 |
| 20 | 设计整体荒谬：承诺全面落空、抽象层层叠加无收益、技术决策无据可查；代码像"在干活"的表演 |

核查清单：
- **承诺-实现核对**：读 README/文档列承诺 → 逐条代码验证。声称"性能提升"→ 核实是否真降低复杂度/开销，还是加了开销（多余抽象、全量复制、冷路径缓存）反而更慢；"可扩展"→ 是否有真实第二实现/扩展点；"支持功能 X"→ 真实现还是占位/TODO。
- 过度工程：简单问题是否套装饰性模式（唯一实现的工厂/接口/抽象基类）。
- 技术思维证据：代码/文档里有无测量、权衡、取舍痕迹；还是"用了 XX 模式所以好"式许愿。
- 测试/构建：是否给维护者安全感（真实断言、覆盖关键路径），还是空壳/占位。

## 维度 2：可追踪性与心智负担（权重 25）

评估"一个人类维护者能不能追踪请求→代码、安全地改动"。这是"愿不愿意维护"最直接的来源。

| 锚点 | 特征 |
|------|------|
| 90 | 请求→代码可追踪：点开功能，逻辑在明确边界内；改动一处通常只看 1-2 处；无 god-function；逻辑边界与文件边界一致。**允许若干较大文件（职责尚可辨认）与少量跨模块复制粘贴**——只要不显著抬高追踪成本，不降出 90 |
| 70 | 基本可追踪，偶有跨文件跳转或逻辑分散，但能顺藤摸瓜；个别大文件但职责可辨认 |
| 45 | 追踪被抽象层/散落逻辑打断、要跨互不相干的文件；核心逻辑混杂在少数 god-file/god-function；改动一处牵动多处且易漏 |
| 20 | 完全无法追踪：逻辑全堆 1-2 个文件/函数；改动任何一处都心惊胆战；人类根本不愿意碰 |

核查清单：
- 挑核心功能从入口追踪到落地，数跨几个文件、被几层打断。
- god-file 检测：文件/函数大小分布。核心逻辑集中在超长函数/超大文件 → 触发 G1 闸门。
- 改动影响面：改公共函数/数据结构要同步改几处；全局状态/拷贝传参耦合多深。
- 隐藏依赖：有没有"不读 X 就不知道这里改到别处"的情况。

## 维度 3：人类可读性与自我解释性（权重 20）

评估"代码本身能不能让人读懂，注释/文档是帮人还是碍人"。

| 锚点 | 特征 |
|------|------|
| 90 | 命名直接传达意图；代码自我解释；注释讲"为什么"（约束、权衡、坑）；README 讲人话且与实现一致。**允许个别风格刺点、个别复述型注释**——不构成噪音就不降出 90 |
| 70 | 大体可读；部分命名需查上下文；注释多数有用，少量复述/清单式；README 基本真实 |
| 45 | 命名无语义（`data`/`result`/`tmp`/`item` 泛滥）；代码读不出意图；注释复述操作或写给 AI/清单看（每个函数一句"该函数用于……"）；README 与实现脱节 |
| 20 | 代码几乎无法读懂：命名与行为不符、注释噪音/幻觉、逻辑绕弯；只能靠 AI 才能"读懂" |

核查清单：
- 命名帮人懂还是徒有其表：对照 `grep` 的 `temp|tmp|data\d|result\d|foo|xxx`。
- 注释讲"为什么"还是复述操作？有无幻觉引用？
- **为谁写的注释**：每个函数都有 docstring 但复述签名/操作、真正难处没解释——是写给 AI/清单看的；面向 AI 编码过程的标记（Codex/探针/agent 留痕）直接记入 AI 过程指纹。
- README 真实性：目录说明与事实一致？声称的功能代码里有没有？

## 维度 4：AI 屎山与许愿痕迹（权重 30，**反向计分**）

评估"项目里 vibe coding / AI 生成的本质痕迹有多少"。**痕迹越多，分数越低**。信号清单与许愿检测协议见 `references/ai-slop-signals.md`。

| 锚点 | 特征 |
|------|------|
| 90 | 无承诺背离、无 AI 过程指纹、无结构性 god。**允许人类正常债务**（个别复制粘贴、个别死导出、个别大文件但职责可辨认）——这类不构成"AI 屎山"，不重罚 |
| 70 | 零星信号（个别未使用导入、个别模板腔注释、个别文档小脱节），正常开发残留，不影响维护 |
| 45 | 信号成规模：承诺-实现背离（许愿）、AI 排查残留、为 AI 的过程标记、结构性 god-file/god-function、系统性复制粘贴变体 |
| 20 | 信号泛滥：大面积承诺落空、AI 过程指纹遍布热路径、god-function 承载全部核心逻辑、注释全为 AI 写的、死代码与幻觉成堆 |

打分要点：
- 权重 30，是影响总分最重的单维。一处重大许愿证据（声称的性能优化实际加开销）或一处触发硬闸门的结构性事实，就足以压到 70 以下；成规模压到 45 以下。
- **"表面规范但设计荒谬"是高分陷阱**：注释齐全、文档漂亮、命名一致、测试量很大，但核心是 AI 过程指纹 + 结构性 god——不要被规范/工程表面骗了，回到维度 4 重罚并触发闸门。
- **人类正常债务 vs AI 过程指纹**：前者（复制粘贴/死代码/大文件）轻扣；后者（AI 标记/调试残留/god-function）重扣。
- 同一文件连续多种信号（幻觉注释 + 死代码 + 吞异常 + god）记"污染集中"，扣分更狠。
