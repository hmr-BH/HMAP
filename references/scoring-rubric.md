# 分维度打分标准（scoring-rubric）

本文件定义五个评估维度各自的 0-100 原始分打分细则。打分时逐条对照锚点特征，取最贴近的一档，再按"部分符合"小幅上下调整（±5 以内）。**每个判断必须有 `文件:行号` 证据支撑**。

## 总则

1. 原始分先给，再乘以权重求加权分（可读性 25 / 注释文档 20 / 架构 25 / AI 屎山 15 / 工程规范 15）。
2. 锚点分数用 90（优秀）、70（正常）、45（较差）、20（极差）四档描述；介于之间用 ±5 档取整。
3. 同一处证据可支撑多个维度，但要分别写清楚它影响哪个维度的哪个分。
4. 若某维度证据不足（如小脚本没有架构可言），按"该项证据不足，不惩罚不奖励，取 70 基线并声明"处理，不得因此虚高总分。

---

## 维度 1：代码可读性（权重 25）

评估"一个人类程序员能否顺畅地跟随代码的心智路径"。

| 锚点 | 特征 |
|------|------|
| 90 | 命名完全语义化（变量/函数/类名直接说明意图），无 `data1`、`temp`、`foo`、`x2` 类命名；函数普遍短小（多数 <40 行）且单一职责；控制流直接，嵌套 ≤3 层；格式化风格统一 |
| 70 | 命名基本语义化，少量缩写或通用名但可辨认；多数函数不长，个别函数偏长或有 3-4 层嵌套但能读通；风格基本一致 |
| 45 | 命名部分无意义（`item`、`data`、`result`、`tmp` 频繁出现）；大量长函数（数百行）、深嵌套、面条式条件分支；同一函数职责混杂；换行/缩进混乱 |
| 20 | 几乎无法跟随心智路径：命名与行为不符、逻辑绕弯（能直接做的偏要绕）、魔法数字泛滥、大段复制粘贴的变体代码 |

核查清单：
- 命名是否反映意图（对照 `grep` 出的 `temp|tmp|data\d|result\d|xxx|aaa|foo` 等）
- 最大函数/文件的行数与嵌套深度
- 是否有明显可简化却绕弯的逻辑（加分项）
- 格式化一致性：同文件混用风格（如 tab/空格混排、命名大小写混用）扣分

## 维度 2：注释与文档质量（权重 20）

评估"注释与文档是否帮助理解，而非制造噪音"。

| 锚点 | 特征 |
|------|------|
| 90 | 注释全部讲"为什么"（约束、权衡、坑），几乎不存在复述操作的注释；无逐行废话注释；公共 API 均有高质量文档注释（功能/参数/返回值）；README 与代码实际一致，能直接照做 |
| 70 | 绝大多数注释有用；少量"复述型"注释或陈旧注释，但不构成噪音；公共函数多数有文档注释；README 基本可用、小处过期 |
| 45 | 注释只描述操作（`// 循环遍历数组` 这类），不讲原因；存在大量冗余/逐行噪音注释；部分文档注释照抄签名无信息量；README 与代码明显不符 |
| 20 | 注释垃圾：大量幻觉注释（引用不存在的函数/文件/行为）、注释与代码矛盾、注释纯粹凑字数；README 缺失或完全是模板占位；或关键逻辑完全没有注释让人读不懂 |

核查清单：
- 注释是否回答"为什么这样做"，还是"这行代码在做什么"
- 有无幻觉引用：`grep` 注释中提到的函数/文件名，到代码里验证是否存在
- 注释/文档是否与代码矛盾（改了代码没改注释）
- 中文注释的质量：是否口语化废话、错别字、AI 模板腔（如"该函数用于实现……"每处都来一句）
- README 是否真实反映项目：能否照 README 跑起来、目录说明是否与事实一致

## 维度 3：架构设计（权重 25）

评估"项目是否便于后续维护与拓展"。

| 锚点 | 特征 |
|------|------|
| 90 | 分层/模块边界清晰，目录结构直接传达意图；职责单一，依赖方向合理（低层不反向依赖高层）；核心流程易追踪；新增功能有明确落点（开闭原则实践良好）；依赖清单干净无冗余 |
| 70 | 模块划分基本合理，偶有边界模糊或跨层调用，但核心思路清楚；目录结构大体传达意图；扩展点部分明确 |
| 45 | 架构意图不明：分层混乱或完全没有分层、到处循环依赖、相似逻辑分散在互不相干的位置；目录命名不传达意图（`utils`、`misc`、`helpers` 大杂烩）；单文件数千行 |
| 20 | 无架构可言：所有代码堆在一起、依赖方向随机、模块之间靠全局状态/拷贝传参耦合；改动一处牵动全身；重复造轮子实现语言自带能力 |

核查清单：
- 目录结构与模块命名是否说明"这块是干什么的"
- 有无循环依赖、跨层直接调用（如 UI 层直接操作数据库）
- 有无超大文件（>1500 行）与超小碎片文件（几十个几行的文件）并存
- 新增一个典型需求（如加个新接口）时，改动会落在哪里、是否集中
- 依赖清单里有无明显没用到的库（与 import 对照）

## 维度 4：AI 屎山痕迹（权重 15，**反向计分**）

评估"项目里 vibe coding / AI 生成的屎山特征有多少"。**痕迹越多，分数越低**。详细信号清单与正反例见 `references/ai-slop-signals.md`，本维度只列打分锚点。

| 锚点 | 特征 |
|------|------|
| 90 | 几乎找不到屎山信号：无明显死代码、无过度工程、无幻觉注释、无拼凑感 |
| 70 | 零星信号：个别未使用导入或少量模板腔注释，可视为正常开发残留，不影响维护 |
| 45 | 信号成规模：死代码/未使用导出多、为简单问题套工厂/抽象/接口、同一文件内风格突变、无意义 try-catch 吞异常、注释只描述操作 |
| 20 | 信号泛滥：大段未被调用的代码与复制粘贴变体、过度分层导致无法追踪、幻觉注释指鹿为马、命名与功能不符、到处是 AI 模板腔 |

打分要点：
- 这是**反向计分**维度：发现一处重大屎山信号（如一整段死代码、一个纯装饰的抽象层）就足以把该维度压到 70 以下；多处成规模的信号压到 45 以下。
- 同一文件里连续出现多种信号（幻觉注释 + 死代码 + 吞异常）记为"污染集中"，比分散的信号扣分更狠。
- 反过来，只有零星残留不扣狠分——判断标准是"是否影响人类维护"，不是"是否零容忍"。

## 维度 5：工程规范与一致性（权重 15）

评估"项目整体的工程纪律"。

| 锚点 | 特征 |
|------|------|
| 90 | 命名/风格全局一致；错误处理策略统一（要么集中要么逐处但同套路）；DRY 做得好，无明显重复大块；有测试且测试断言有意义；构建/运行可验证 |
| 70 | 大体一致，个别文件风格偏移；错误处理大体统一、偶有例外；重复代码有但不多；测试存在、部分偏形式；项目能跑起来 |
| 45 | 风格混杂（同项目里多种命名规范并存）；错误处理矛盾（有的吞、有的抛、有的静默）；大段重复代码；测试多为占位/无断言/`it('should work')` 式空壳；构建或运行存在明显问题 |
| 20 | 无规范可言：风格随心所欲、错误处理完全随机、复制粘贴驱动开发（同一逻辑 N 份拷贝）、无测试、构建脚本损坏或缺失 |

核查清单：
- 全项目 grep 命名风格：是否同语言内混用 `snake_case`/`camelCase`/`PascalCase`（语言惯例允许者除外）
- 错误处理：`except`/`catch` 里是空块、`pass`、`print`，还是真正处理
- 测试：`grep` 测试文件里的断言关键词（`assert`、`expect`、`should`、`it(`），核对是否有实际断言而非占位
- 构建/运行：按 README 或构建脚本能否在目标环境启动（只做静态判断，不在被测项目里实际跑构建时，标注"未实际运行"）
